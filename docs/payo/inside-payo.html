Repository anatomy

How the code fits together

Payo lives in the payo/ TypeScript workspace. Follow a command inward from either client. The factory decides which workflow step comes next. The server supplies the concrete tools that perform it.

Web or CLI→HTTP server→Factory workflow→Injected ports
Runtime call path · A port is an interface for a capability such as running an agent or reading a Git branch.

Does Payo follow a microkernel architecture?

Partly. The kernel supplies reusable run state, event logging and agent execution. The factory builds planning, implementation and publication on top. The dependency points inward: the factory uses the kernel, while the kernel’s only workspace dependency is contracts.

Look at how a new capability gets added. A different GitHub client can implement the existing CodeHost port and be selected in the server’s wiring. A new workflow needs an explicit entry point in the run service, which imports and calls the supported factory workflows directly. Payo has a microkernel-like core, with ports and adapters providing the concrete extension points.

Architecture in practice

Patterns you can see in the code

Take one question through the system. A publication run has restarted after a push. How does Payo decide whether it can continue?

Layered domain policy

The factory’s application layer reads the remote head and passes three facts to reconcileRemote. The domain function can decide what to do with those values alone. Changing the ownership rule belongs here. Changing how Git reads the head belongs in the Git adapter.

Decision function ↗ Policy tests ↗

Ports, adapters and dependency injection

The workflow receives a PublicationDeps object. Its repository port can inspect or push a commit. Its codeHost port can find or create a PR. The server constructs both implementations at startup. A fake can answer the same calls during a test, so the real decision and retry logic still run.

PublicationDeps ↗ Port ↗ Wiring ↗

Event-sourced run state

When a run writes a batch, the kernel validates every event and applies the reducer in sequence. It then asks the store to append against the expected previous sequence. On reopen, it folds the saved events to reconstruct the run and records any recovery events. A failed append leaves the in-memory run log at its last committed state.

commit / openRun ↗ Write serialization ↗ Reducer ↗

Checkpointed workflow and reconciliation

A checkpoint tells the factory which stage needs attention. Publication saves a push intent before contacting Git. If the process stops after Git succeeds, explicit resume can compare the remote head with the reviewed commit. A match with saved intent lets the workflow proceed to draft creation. A mismatch raises a gate for inspection.

Effect ordering ↗ Checkpoints and gates ↗

Feature-oriented UI and shared contracts

The publication form and its API function live together in the run-workspace feature. The shared HTTP client handles transport. Contract schemas validate the request on the server and the preview response in the browser. For a new preview field, follow its schema through the preview builder to the consuming component.

Publication schemas ↗ Preview builder ↗ Feature API ↗

Executable architecture boundaries

The repository tests the import rules themselves. Factory domain code can depend on contracts and kernel state types. Publication orchestration receives its external capabilities through ports. Boundary tests also check for cycles and restrict which web features can import one another. These tests explain where a new dependency can go.

Workflow

Where the work changes hands

A PR unit is a group of ordered phases in the approved plan. A plan can describe several PR units. You choose which one to execute and when to publish its result.

Plan & review

Payo resolves the Jira ticket or direct prompt and creates a planning workspace. A planner proposes phases and PR units. Reviewers examine the plan in parallel, a verifier evaluates findings, and a reviser can send a new version through review.

Answer open questions, inspect phase assignments, then approve or request changes. Approval ends this run.

Workflow source ↗

Implement & check

Select a PR unit, preview its naming and confirm. Payo pins the plan, prepares a Git worktree and executes phases in order. Each phase gets a fresh implementer context. The engine runs configured checks, coordinates review and allows bounded repairs.

Inspect phase receipts, checks and final PR-level review. A successful execution leaves a reviewed local commit and worktree.

Workflow source ↗

Preview & publish

Preview the target, branch, title and body. Confirming creates a publication child. Payo checks the base, pushes the reviewed commit, verifies the remote branch and creates a GitHub draft PR.

Open the recorded PR link for human review. Another PR unit starts only when selected.

What happens when a run stops?
A gate records why work paused and which commands can continue it. After a server interruption, inspect the gate and explicitly resume. Execution checks the retained worktree and reconciles partial edits. If approved requirements need changing, a corrected planning run goes through approval again while the original execution stays paused. Publication checks remote state before retrying. One action through the stack

Trace “Create draft PR”

Start with the button in an execution workspace. Follow the request to see which layer validates input, which decides whether publication is safe, and which performs the remote operation.

  1. Submit the reviewed preview

    The form collects the title and body. The feature API sends an authenticated POST to /api/v1/runs/{executionId}/publish.

    Form ↗ publishRun ↗

  2. Accept the command

    The HTTP route validates the payload. The run service calls beginPublication, schedules a newly created run and returns its ID. The client can open that child while the server continues working.

    Route ↗ publish ↗

  3. Record intent and perform the operation

    The factory checks the reviewed commit and base against the publication record. Before a push or draft creation it saves its intent. Git and GitHub adapters carry out the calls. A retry can inspect the remote branch and matching PR before deciding whether to continue or raise a gate.

    executePublication ↗ Reconciliation decisions ↗

  4. Show the result

    The factory records the PR and ends the run as published. The browser follows ordered server-sent events and refreshes workspace data. The publication view displays the recorded result or recovery action.

Persistence

What survives a restart

The default data directory is ~/.payo. Three kinds of evidence answer different questions when you inspect a run.

Event log

What happened? Ordered SQLite events record step starts, attempt outcomes, gates and run endings. The kernel folds them into the current run state.

Artifacts & checkpoints

What did a step use? Content hashes identify saved plans, review output and other evidence. Checkpoints track the workflow stage and references needed to continue.

Working files

Where are the edits? A working plan can be edited and reviewed again. An execution worktree retains the branch and partial changes so recovery can inspect actual Git state.

Local setup

Run the offline example

Use Node 24 and pnpm 10.9. Run the repository setup command from the checkout root to install dependencies, create a starter config if needed and run preflight.

uv run scripts/setup.py

Start the server

In one terminal, run from the checkout root. Fake mode supplies scripted agents and tool responses.

pnpm -C payo payo serve --dev-fakes

Connect the console

In another terminal, print the token and start Vite. Open 127.0.0.1:5173 and enter the token. The default API port is 7331.

pnpm -C payo payo token
pnpm -C payo web:dev

Start a planning run with the fake Jira ticket ABC-123. Answer q1, approve the plan, then select pr-1 to exercise its two phases. Execution requires configured checks.

What changes in real mode?
Start the server without --dev-fakes. Configure models and execution checks in ~/.config/payo/config.toml. Pi needs provider credentials, and the target repository needs the role instructions committed at the selected base. Jira intake uses authenticated acli. Publishing uses Git push access and authenticated gh. Restart the server after changing TOML settings.
